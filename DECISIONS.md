# Decisions

## 2026-07-29 — Hosting: Vercel, not the ThinkPad
**Context:** PRD targets 10k-100k concurrent users; this workspace's other services run on a personal always-on ThinkPad (neon-mcp-gateway).
**Considered:** self-hosting on the ThinkPad like the MCP gateway/Hindsight/etc. (nginx + systemd, matching `topology.tinyminotaur.co`); Vercel.
**Chose:** Vercel. tinyminotaur.co's main site and MTG Heatmap Dashboard already deploy this way; Vercel's usage-based pricing means the beta-scale build and a real growth-scale build are the same codebase, no rewrite if it takes off. Built as a friend-group beta for now — the PRD's growth numbers are north-star targets, not Phase 0 requirements.
**Side effects:** custom domain `jury.tinyminotaur.co` added in Vercel project settings (TIN-461), not nginx/systemd.

## 2026-07-29 — Deploy flow: GitHub-first, not Vercel CLI
**Context:** Vercel supports both a CLI-push workflow and a GitHub-integration workflow (auto-deploy on push + PR previews). Josh asked to confirm linking Vercel directly to GitHub.
**Considered:** Vercel CLI deploys (would need a Vercel token/local auth on this box — attempted, CLI wasn't authenticated here); GitHub-linked auto-deploy.
**Chose:** GitHub-linked. Agent creates + pushes the repo; Josh imports it into Vercel via the dashboard (one click, auto-detects Next.js). No Vercel CLI/token needed anywhere in the workflow going forward.
**Side effects:** TIN-461 (Vercel provisioning) is now blocked by TIN-462 (repo must exist first), reversed from the original ordering.

## 2026-07-29 — DB driver: @neondatabase/serverless, not @vercel/postgres
**Context:** MTG Heatmap Dashboard (the closest precedent in this workspace) uses `@vercel/postgres` for its user/session tables. Installing it here during scaffolding surfaced an npm deprecation notice: `@vercel/postgres` is deprecated — Vercel migrated its Postgres offering to Neon as a native integration and its own migration guide points new projects at Neon's SDK directly.
**Considered:** following the MTG Heatmap precedent exactly (`@vercel/postgres`); using Neon's own `@neondatabase/serverless` driver.
**Chose:** `@neondatabase/serverless`. No reason to start a new project on a package the vendor is actively steering people away from. MTG Heatmap's use of `@vercel/postgres` predates this deprecation and isn't touched by this decision — separate project, separate migration if Josh wants it later.
**Side effects:** `TIN-463`'s data-model work should target `@neondatabase/serverless`'s query API, not `@vercel/postgres`'s `sql` tagged template (similar shape, different import). Confirm the exact env var name Vercel injects for the Postgres connection string once TIN-461 provisions the DB — historically `POSTGRES_URL`, may differ under the Neon-native integration.

## 2026-07-29 — Auth: Neon Managed Better Auth (Magic Link plugin), not hand-rolled Auth.js/Lucia
**Context:** original plan (see AGENTS.md, TIN-461/463 as first written) was passwordless email magic-link auth via Auth.js or Lucia, backed by Resend. When Josh provisioned Neon Postgres through Vercel's marketplace integration (TIN-461), Vercel also auto-injected `NEON_AUTH_BASE_URL`, `VITE_NEON_AUTH_URL`, and `NEON_PROJECT_ID` — these are for Neon's own managed auth service ("Neon Auth," built on the Better Auth library), not leftover/unused vars.
**Considered:** hand-rolling magic-link auth with Auth.js or Lucia (Lucia specifically is a bad idea regardless — its own maintainer deprecated it and stopped recommending it); using Neon's Managed Better Auth, which ships a first-class Magic Link plugin (toggle in Neon Console -> Auth -> Plugins) and uses Resend as its recommended production email provider for delivery.
**Chose:** Neon Managed Better Auth with the Magic Link plugin enabled. It's already provisioned (came free with the Neon integration), needs no custom token-generation/session code from us, and uses the same Resend API key already sitting in Vercel env vars for the actual email send — the pieces Josh already set up assemble into the exact auth flow the PRD calls for, with less code to write and maintain.
**Side effects:** TIN-463 rewritten to integrate against Neon Auth's client/API instead of building magic-link logic from scratch. Need to verify during TIN-463 implementation whether the Resend key needs to be separately configured inside the Neon Console's Auth settings (Neon Auth runs on Neon's infra, not inside our Vercel deployment, so it may not auto-read our Vercel env vars) — flagged, not yet confirmed.

**Follow-up bug #1 (found live, 2026-07-29):** the deployed sign-in page rendered a completely empty card — no email field, no button, nothing, even server-side. First hypothesis: `@daveyplate/better-auth-ui`'s `AuthUIProviderProps` has separate `magicLink`/`emailOTP` booleans, both defaulting `false`; `credentials={false}` was set but `magicLink` was never explicitly turned on. Added `magicLink` to `NeonAuthUIProvider` — build succeeded, but the card was **still** completely empty after deploy.

**Follow-up bug #2 (the real root cause):** added a temporary debug component rendering `useContext(AuthUIContext)`'s actual runtime value directly into the page — it came back essentially empty (`{"viewPathsKeys": null}`, `magicLink`/`credentials`/`basePath` all `undefined`), even though the compiled bundle provably had `magicLink: true` baked into the `NeonAuthUIProvider` call site (verified via `curl`+`grep` on the deployed JS chunks). This means the Provider's context value was never reaching the Consumer at runtime — a module/context-duplication bug (almost certainly a dual ESM/CJS package-instance hazard in this specific Turbopack + Next.js 16 combination), not a config mistake. Confirmed via direct evidence, not just static prop tracing.

**Decision:** drop `@neondatabase/auth-ui` and `@daveyplate/better-auth-ui` entirely rather than keep debugging bundler internals of a third-party UI kit. We only need a single email-in/magic-link-out flow — not the organizations/teams/passkeys/2FA surface the kit provides — so a ~70-line custom form calling `authClient.signIn.magicLink()` directly is both simpler and fully within our control. Client now built directly on `better-auth/client` + `better-auth/client/plugins`'s `magicLinkClient()` (pointed at our own `/api/auth` proxy), since `@neondatabase/auth/next`'s `createAuthClient()` wrapper takes no config and can't register plugins. `@neondatabase/auth/next/server`'s `createNeonAuth()`/`auth.handler()` is unaffected and stays — that side is just an HTTP proxy, no client-side plugin/context system involved.

**Side effects:** `app/providers.tsx` and the CSS import for `@neondatabase/auth-ui/tailwind` removed. `app/auth/[pathname]/` (dynamic, multi-view) replaced with a fixed `app/auth/sign-in/page.tsx`. Dashboard's `UserButton` replaced with a plain `SignOutButton` calling `authClient.signOut()` directly. Lesson: when a value is provably correct at the "config" layer but the DOM output still doesn't reflect it, don't keep tracing static code — render the actual runtime value directly into the page (or log it) to see what the consumer really receives. That one probe cut through several rounds of plausible-but-wrong static-analysis theories (caching, redeploy snapshots, prop-spread order) in a single step.

## 2026-07-29 — Client points directly at NEON_AUTH_BASE_URL, not our own /api/auth proxy
**Context:** after fixing the empty sign-in form, clicking the real magic-link email just bounced back to `/auth/sign-in` instead of landing on `/dashboard` with a session. The email's verify link points at Neon's raw hosted domain (`ep-xxx.neonauth...neon.tech`), not our app's domain — and Neon's own docs/blog independently confirm this is a known rough edge: the session cookie is `HttpOnly`, `SameSite=None`, scoped to Neon's own domain, and "architectures where frontend and backend are separate deployments" (exactly our Vercel + neon.tech setup) are flagged as not fully smoothed over yet.
**Considered:** keep the client pointed at our own `/api/auth` proxy (original setup, matches the server-side `auth.handler()` proxy pattern) and try to bridge the cross-domain gap ourselves; or point the client directly at `NEON_AUTH_BASE_URL`, matching Neon's own official blog example (`neon.com/blog/auth-that-just-works-in-vercel-previews`) verbatim.
**Chose:** direct `NEON_AUTH_BASE_URL`. It's Neon's own documented pattern, needs less custom bridging code from us, and lets the browser's native same-origin cookie behavior do the work for client-side session calls (`authClient.getSession()`, `signIn.magicLink()`, etc.) since those now go straight to the domain the cookie actually lives on.
**Side effects:** added `NEXT_PUBLIC_NEON_AUTH_URL` as a new Vercel env var (Vercel's Neon integration only auto-provisions a `VITE_`-prefixed copy, useless for Next.js client bundling — a real gap in the integration, not a Josh mistake). Value set via `vercel env add` using the domain visible in the actual magic-link email, since Vercel masks "Sensitive" var values even on CLI `env pull` (confirmed empirically — every sensitive var read back as an empty string). `lib/auth/client.ts` now uses `NEXT_PUBLIC_NEON_AUTH_URL` as `baseURL` instead of `/api/auth`. **Open question, not yet resolved:** whether our own SERVER-SIDE `auth.getSession()` (`lib/auth/server.ts`, used by `proxy.ts` middleware and the dashboard Server Component) can see a session established this way at all, since the browser's request to *our* domain never carries Neon's cross-domain cookie — server-side route protection may need a different mechanism than "read the incoming request's cookies." Verify live before considering TIN-463 fully done.

**Result: still broken.** Tested live with a fresh (non-expired) magic-link email — clicking it never even reached `/dashboard`, no cookie appeared on either domain (confirmed via DevTools Application > Cookies), and the browser landed straight back on `/auth/sign-in`. Whatever's happening (verify failing silently, or succeeding but the cross-domain cookie genuinely never reaching either side usably), Neon Managed Better Auth's cross-domain story is not workable for this deployment shape right now.

## 2026-07-29 — Dropped Neon Managed Better Auth entirely; fully custom magic-link auth
**Context:** after the UI-kit context bug, the deprecated-package swap, and now a confirmed-broken cross-domain cookie flow, Josh flagged (correctly) that basic auth infrastructure should not have cost this much debugging effort — a real signal to stop fighting the managed service, not push harder on it.
**Considered:** keep debugging Neon Auth's cross-domain cookie handling (open-ended, no guarantee of a fix, Neon's own docs already flag the architecture as unsupported); switch to a fully custom magic-link implementation using only things already wired up (Postgres, Resend).
**Chose:** fully custom. `users` + `magic_links` tables in our own Postgres (`lib/db.ts`); `POST /api/auth/request` generates a token and emails it via Resend directly (`resend` npm package); `GET /api/auth/verify?token=` validates the token (15-min expiry, single-use), upserts the user, and sets a signed session cookie **on our own domain** — no second domain involved anywhere, so no cross-domain cookie question can even arise. Session cookie is a minimal hand-rolled HMAC-signed payload (`lib/auth/session.ts`) rather than pulling in another library (e.g. `iron-session`) — simple enough to not need one, and every line of it is something we can read and debug directly instead of treating as a black box.
**Side effects:** removed `@neondatabase/auth`, `better-auth`, `@neondatabase/auth-ui`, `@daveyplate/better-auth-ui` entirely. `proxy.ts` now verifies the session cookie directly (Next.js 16's Proxy defaults to the Node.js runtime, so Node's `crypto` module — used for the HMAC — works fine there, no edge-runtime workaround needed). Repurposed the already-provisioned `NEON_AUTH_COOKIE_SECRET` Vercel env var as the generic session-signing secret rather than asking Josh for yet another env var round trip — the name is now stale/misleading (it's not Neon-Auth-specific anymore) but renaming it means another Vercel trip for zero functional benefit. `NEON_AUTH_BASE_URL`, `NEXT_PUBLIC_NEON_AUTH_URL`, `VITE_NEON_AUTH_URL`, `NEON_PROJECT_ID` are now unused dead env vars in Vercel — harmless to leave, fine to remove later if Josh wants to tidy up.
**Email sending domain:** uses Resend's shared `onboarding@resend.dev` testing address for now — works without domain verification, fine for beta, but needs a verified custom sending domain in the Resend dashboard before real launch (mail clients/spam filters trust it far more, and `resend.dev` may eventually rate-limit or restrict recipients).

**Vote options:** added `cases.vote_options` (jsonb, defaults `["Guilty", "Not Guilty"]`) per PRD 2.1's note that non-legal dilemmas may need different option pairs (Yes/No, Option A/Option B) -- keeps the ballot UI generic rather than hardcoding "Guilty/Not Guilty" everywhere.

## 2026-07-31 — Launch case catalog (TIN-469): data files, not a CMS
**Context:** Phase 0 engineering is largely In Review; the remaining MVP content gap is 20-25 real Wikipedia-sourced cases. A full authoring UI would be premature for a friend-group beta.
**Chose:** a typed catalog under `src/data/cases/` (one file per case + `index.ts`), loaded by `seedCases()` via `ON CONFLICT (slug) DO UPDATE` for content fields. `drop_date` is set on insert only so re-seeds cannot reshuffle the calendar out from under live players. Anna Pou stays at `2026-07-29`; the other 24 drop daily from `2026-08-01` through `2026-08-24` so current beta testing is not displaced mid-day. Difficulty aimed at PRD 3.4's weekly mix (~3 easy / 2 medium / 1-2 hard): overall 11 easy (1–2) / 7 medium (3) / 7 hard (4–5), scheduled so the first three full weeks each land near that mix.
**Content rules (unchanged, enforced in authoring):** every case has a live Wikipedia `source_url` (verified via HTTP before writing); briefs are original paraphrase; `brief`/`evidence`/`counter_arguments`/`tldr`/`key_facts` never state or imply the real outcome; reveal-only fields hold `real_verdict`/`historical_context`; Central Park Five is framed as the 1990 evidence world with exoneration only in the reveal. Non-criminal dilemmas use custom `vote_options` (Amistad, Tinker, Leopold & Loeb sentencing, Pistorius murder vs culpable homicide).
**Side effects:** no CMS/admin UI yet — editing a case is a PR. If the calendar needs to slip, change `drop_date` in the catalog and ship; existing rows keep their original dates unless manually migrated.

## 2026-07-30 — Dark theme only; fixed a real contrast bug
**Context:** Josh's screenshot showed the new TL;DR/key-facts text nearly invisible on his phone. Root cause: `globals.css` set `--background`/`--foreground` via `@media (prefers-color-scheme: dark)`, so the page shell followed the *system* theme, while every component (sign-in, dashboard, case brief, deliberation room, reveal) was hardcoded assuming a dark backdrop with light text. On a light-system device, the shell went white while component text stayed light-colored -- near-white text on a near-white page.
**Chose:** one dark theme, always, removed the light/dark media query entirely rather than retrofit every component with `dark:` variants. Simpler to get right and verify than maintaining two palettes for a pre-launch beta with one operator.
**Side effects:** `app/page.tsx`'s conditional `dark:` classes simplified to their dark-only equivalents (was the only file using the `dark:` prefix at all -- confirmed via grep before and after).

## 2026-07-30 — Visual redesign of the case brief: TL;DR, key facts, no real photos
**Context:** Josh: initial case review was "black and white," wanted more visual weight, a TL;DR up front, and to "lead with the most interesting point and what is needed for the user to decide."
**Chose:** two new required case fields -- `tldr` (one-hook-sentence) and `key_facts` (bulleted, scannable facts) -- shown prominently above the full narrative brief, which is now collapsed-by-default ("Read the full account") rather than the primary reading experience. Hero header uses a gradient + large icon for visual weight instead of plain text. Evidence exhibits got a simple icon per item (keyword-matched: toxicology→🧪, statement→📢, conditions/timeline→🏥, testimony→🗣️, default→📄).
**"Pictures" -- deliberately not real photos:** sourcing real images for historical cases hits the same licensing question the Wikipedia-sourcing policy already solved for text (real news/court photos are often NOT public domain even when the facts themselves are). Rather than guess at licensing per-image, this pass uses generated visual treatment only (gradients, icons, color, typography). Real photo sourcing (e.g., verified public-domain government/archive images specifically) is a distinct future task, not bundled into this one.
**Same no-spoiler rule applies to the new fields:** `tldr` and `key_facts` must never state or imply the real outcome, same as `brief`/`evidence`/`counter_arguments` (see the earlier outcome-spoiler entry). Verified the seed case's new content against this before shipping.
**Side effects:** new `cases.tldr` (text) and `cases.key_facts` (jsonb array) columns; seed case backfilled via the existing `ON CONFLICT DO UPDATE` pattern. TIN-469 (bulk case authoring) must include both fields for every future case going forward.

**Side effects:** new `DEMO_MODE_SECRET` env var (Production), set directly via `vercel env add` this time -- no web-form typo risk since the CLI path is now proven reliable.

## 2026-07-29 — Fixed silent failure when posting to the deliberation thread
**Context:** Josh: "when I tried to add a comment it never logged... And then it said deliberation is already ended." Two things going on, both real: (1) `sendMessage` cleared the input immediately on submit and never checked the response status, so a failed POST looked identical to a successful one -- no error, no indication anything went wrong, message just silently never appeared. (2) The actual failure reason: his group has 1 member, and PRD 2.2's quorum rule ("all vote" for groups <=4) is trivially satisfied the instant that one person casts a Phase 1 vote -- so the deliberation auto-resolves to unanimous almost immediately (a lone juror trivially "agrees with themself"), leaving almost no real window to test the mid-deliberation thread/vote-changing UI with a single-member group.
**Fixed:** `sendMessage` now checks `res.ok`, shows a real error message on failure, and only clears the input on success (so a failed attempt doesn't lose what was typed).
**Not a bug, just a testing-scale limitation:** with only one real working test account (Resend sandbox, same limitation as TIN-467/465), there's no way to keep a deliberation in 'pending' long enough to exercise the thread/vote-changing UI properly -- that genuinely needs 2+ people voting async, which is exactly the real multi-person testing this workspace has been blocked on throughout TIN-465/466/467.

## 2026-07-29 — Reveal: shared solo/group data layer, hung juries still get a reveal
**Context:** TIN-468, the last Phase 0 issue. PRD 2.5's four layers: individual votes, group/solo final verdict + swing, real historical outcome + community stats, shareable card.
**Design:** `lib/reveal.ts` unifies solo and group into one `RevealData` shape and one `getGroupRevealData`/`getSoloRevealData` pair, both feeding a single `<Reveal>` component (`src/components/reveal.tsx`) used from both `DeliberationRoom` (group, once resolved) and `SoloPhase2` (solo, once the final choice is submitted) -- one implementation, not two. `GET /api/reveal-card` renders the actual shareable PNG via `next/og`'s `ImageResponse` (Satori-based; only flexbox + a CSS subset supported, so it's plain inline `style` objects, not Tailwind classNames -- that engine doesn't process our stylesheet at all).
**Reveal timing:** available immediately once resolved (group deliberation concluded, or solo's Phase 2 decision made) -- not gated behind the PRD's 24h global window. Matches PRD 2.5's own "or whenever deliberation concludes for that group, if they finish early" clause, and keeps the feature testable without an artificial day-long wait.
**Bug caught before shipping:** the initial `getGroupRevealData` required `deliberation.final_choice` to be non-null, which silently excluded hung juries (final_choice is null by design for `status='hung'`) from ever getting a reveal at all -- exactly the outcome the PRD's own success metrics call out as expected ~40% of the time. Fixed: hung juries get a full reveal too, with Layer 2 showing "No consensus reached (Hung Jury)" instead of a verdict; community-stats aggregation already correctly excludes them from the vote-choice tally (a hung jury isn't a vote for either side).
**Community stats:** aggregated across every RESOLVED group deliberation's `final_choice` plus every solo player's phase-2 choice for the case -- i.e., completed decisions only, not raw Phase 1 leanings (closer to PRD's "72% of groups today convicted" framing than counting initial-vote noise).

## 2026-07-29 — Phase 2 group deliberation: MVP simplifications
**Context:** TIN-465 (PRD 2.2) is the most complex mechanic -- quorum, a clock, a thread, vote-changing, and three possible resolutions (unanimous/majority/hung).
**Design:** new `deliberations` table (one row per case+group once quorum is met). Quorum: all members voted for groups <=4, >=50% for groups 5-8 (PRD 2.2). Clock: 3 hours for groups <=4, 6 hours for 5-8 (PRD's "3hrs, extendable to 6-8hrs for larger/complex cases" -- simplified to size-only, not factoring case difficulty). Vote-changing during deliberation reuses the existing `phase` column: group Phase 2 now allows *multiple* phase=2 rows (each a change, unlike solo's one-shot phase=2), with "current vote" = latest row (any phase) per active juror. Resolution: unanimous is auto-detected on every poll/vote (all active jurors currently agree); majority is an *explicit* action only available in the final 15 minutes (PRD: "a choice, not automatic fallback") via `POST /api/groups/[groupId]/accept-majority`; hung is auto-detected once the clock expires with neither.
**Deliberately not implemented (documented gaps, not bugs):**
- **Deferred juror state** (PRD 2.4: went dark during deliberation) -- everyone who cast a Phase 1 vote is treated as "Active" for quorum/consensus. Detecting "went dark" needs an activity-recency heuristic that adds real complexity for unclear benefit at this stage; revisit if group testing shows it matters.
- **Anonymous juror reasoning snippets** (PRD 2.2 point 2, explicitly optional) -- skipped for MVP scope.
- **Foreperson-style explicit "call for a vote" confirmation** (PRD 2.2 point 5) -- simplified to fully automatic: consensus resolves the instant all active jurors agree, no explicit confirmation step. Reduces one whole interaction pattern (nominate/confirm) for a first pass.
- **Case-complexity-based clock extension** -- clock length depends only on group size, not the case's difficulty rating.
**Testing constraint:** the real multi-person quorum/majority/hung-jury paths can't be live-verified yet -- same Resend sandbox limitation as TIN-467 (Josh can only sign in as one email until a sending domain is verified). Verifiable now: a single-member group triggers quorum instantly (trivial "all voted"), the thread, vote-changing, and unanimous auto-resolution. Majority and hung jury need either a second working test account or the clock to actually expire.

## 2026-07-29 — Solo Phase 2 reuses the phase column, not a separate table
**Context:** TIN-466 (PRD 2.3) needs solo players to see a counter-argument to their Phase 1 vote and affirm/change it, concluding immediately (no group to wait on).
**Chose:** the existing `votes.phase` column already supports 1/2 — solo Phase 2 is just a `phase=2` row (group_id still NULL), same shape group deliberation (TIN-465) will eventually use for its own Phase 2 votes. Added `cases.counter_arguments` (jsonb, keyed by vote_option) so the counter shown is genuinely the argument *against whatever the player chose*, not a fixed direction — required writing a real counter-argument for each side of the seed case, not just one.
**Side effects:** `/api/votes` now accepts an optional `phase` (default 1); phase-2 submission requires an existing phase-1 vote first. Dashboard checks phase 1 and phase 2 votes separately to decide which of `CaseBallot` / `SoloPhase2` / `VotedSummary` to render — this only applies to solo (`group_id IS NULL`); group pages still just lock after Phase 1 until TIN-465 builds real group deliberation.
**Not implemented:** the PRD's 10-minute solo Phase 2 window/timeout. No forced conclusion if a player leaves without deciding -- they'll just see the same counter-argument step again next visit. Low-risk to skip for now (immediate submission is the primary path either way); revisit if it matters in practice.

## 2026-07-29 — Group formation: known gap in the invite-link cold-start UX

## 2026-07-29 — No stored `reveals`/`community_stats` table
**Context:** TIN-463 as originally scoped listed "reveals/community_stats aggregates" as a table alongside votes/messages.
**Considered:** a materialized reveals table updated on write; computing reveal data (swing rate, vote splits, cross-group stats) from `votes`/`deliberation_messages` on read.
**Chose:** compute on read. Same principle as not storing Active/Deferred/Recused as a column (see schema comment in `lib/db.ts`) — a derived value that can drift from its source is worse than a query, and case/group/vote volume is far too small for this to be a real performance problem at friend-group-beta scale. Revisit only if reveal queries actually show up as slow once TIN-468 is built.

## 2026-07-29 — Next.js 16 breaking changes hit during TIN-463 (for future reference)
**Context:** AGENTS.md warns this Next.js version has undocumented-in-training-data breaking changes. Two hit immediately when wiring Neon Auth:
1. The `middleware.ts` file convention is deprecated in favor of `proxy.ts` (same export shape — default export function + optional `config.matcher` — just a rename). `next build` prints a warning but still builds either way; only discovered the rename was mandatory-in-spirit by reading `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/proxy.md` directly.
2. Neon Auth's route handler (`auth.handler()` from `@neondatabase/auth/next/server`) hardcodes an internal `Params` type expecting `{ path: string[] }` — the catch-all route folder **must** be named `app/api/auth/[...path]/`, not `[...all]` or any other name, or TypeScript fails the build with a type-satisfaction error on `RouteHandlerConfig`. Not documented anywhere obvious; found by reading the actual installed `.d.mts` file after a build failure.
**Side effects:** `src/proxy.ts` (not `middleware.ts`), `src/app/api/auth/[...path]/route.ts` (not `[...all]`). If a future Next.js/Neon Auth upgrade changes either of these again, `npm run build`'s own type errors are the fastest way to find the real answer — faster and more reliable than searching docs/blog posts for this particular integration.

## 2026-07-29 — Deliberation thread updates: polling, not WebSockets
**Context:** PRD Section 10.1 suggests "WebSocket or pub-sub" for the deliberation thread; Section 10.3 separately describes the thread as "read-heavy, write-light" and async-friendly.
**Considered:** WebSockets (Pusher/Ably or self-hosted); Server-Sent Events; simple polling.
**Chose:** polling (15-30s interval) for MVP. On serverless (Vercel functions), a long-lived WebSocket/SSE connection is awkward and bills differently than the PRD's own framing of the thread assumes; polling is indistinguishable from real-time for an async deliberation window measured in hours, and is the simplest, cheapest thing to run. Revisit only if user feedback demands snappier updates.
**Side effects:** none yet — implemented in TIN-465.

## 2026-07-29 — Case sourcing: real cases only, Wikipedia as primary source
**Context:** Josh: "each case needs to be entirely real and use the wikipedia article as the primary source." The original PRD appendix included one explicitly fictional example case ("The Vanishing Ledger, inspired by real trials") alongside two real ones, and Section 12 flagged real-photo/court-document copyright risk without a concrete Phase 0 answer.
**Considered:** PRD's original mixed approach (real + "inspired by" cases, loose sourcing); requiring a real Wikipedia article as the primary source for every case.
**Chose:** every case must be entirely real with a Wikipedia article as its primary source. Case briefs are original prose summarizing that article's facts — never copied verbatim, since facts aren't copyrightable but Wikipedia's specific wording is (CC BY-SA, share-alike), and paraphrasing keeps that license off our own content. `cases.source_url` is a required DB field, shown in-app as a visible citation. This both resolves the copyright-risk flag from the original plan and makes the game's factual claims independently checkable, which fits the "teaches genuine history" pitch better than an unnamed advisory board would.
**Side effects:** dropped the fictional appendix example from the case-authoring scope (TIN-469); `cases.source_url` added to the schema (TIN-463); citation display added to the case-brief page (TIN-464) and the reveal's historical-outcome layer (TIN-468).
